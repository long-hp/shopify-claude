# Shopify's `{% stylesheet %}` tag — behaviour and limits

Sources: shopify.dev → Liquid tags → `stylesheet`; Themes → Best practices → "JavaScript and stylesheet tags" and "Performance". Re-read those pages when in doubt; the behaviour can change.

## What Shopify does

- The CSS inside `{% stylesheet %}…{% endstylesheet %}` of **every section, block and snippet** is gathered into **one generated CSS file**, linked from `{{ content_for_header }}` (inside `<head>`). The theme adds no tag for it.
- That file is **subset to the render tree of the current page**: it only contains CSS from liquid files that actually rendered during that request. A section that is not on the page costs nothing.
- Each liquid file contributes its CSS **once**, no matter how many times it renders. Per-instance styling (colour from a setting, an id) stays in inline `<style>` / `{% style %}` plus CSS variables.
- Shopify preloads render-blocking stylesheets with **Early Hints** before the HTML arrives. Links in `<head>` benefit; links in `<body>` do not.

## Why this is the right fit for the theme

| Approach | Requests on the critical path | Discovered | Section dragged into an unexpected page |
|---|---|---|---|
| One `styles.css` | 1 | early (head) | styled, but every page carries every section's CSS |
| Dawn-style split (`stylesheet_tag` inside each section) | 1 + N | late (body, when the parser reaches the section) | styled |
| `{% stylesheet %}` | 2 (shared file + Shopify's generated file) | early (head, Early Hints) | styled, and the page only receives the CSS of sections it has |

## Limits

- **No Liquid inside the tag.** Shopify does not render it; `{{ }}` or `{% %}` inside the CSS causes syntax errors or styles that never apply. Dynamic values → CSS variables set on the markup.
- **One tag per file.** A second tag is a syntax error. The plugin merges the CSS of several scss files that map to the same liquid into one block.
- **The order of CSS inside the generated file is not documented.** Every file's CSS must stand on its own: scope it under the component's own class (`.xo-journal .x`), never rely on order to override another file. The BEM rule of the `scss` skill already covers most of this.
- **A file's classes should only be used in that file or files it renders directly** (Shopify's own guidance, so subsetting stays correct). If section B depends on snippet A's CSS and B stops rendering A, that CSS disappears.
- **HTML that arrives later via AJAX is not in the render tree.** Quick view (`?section_id=quick-view-content`), Section Rendering API (`?sections=`), predictive search (`/search/suggest?section_id=`), product recommendations, pickup availability. The CSS of those sections and of every snippet they render must **stay in the shared stylesheet** → `exclude` in `theme-config/stylesheet.config.json`. `find-ajax-sections.mjs` lists them. Shopify's docs do not spell this case out, so verify quick view on a real store after installing.
- Theme Check (`shopify theme check`) accepts the tag; no extra configuration.

## How to verify on a store

1. Open the home page, DevTools → Network, filter `.css`: you should see the theme's `styles.css` (shared) plus one CSS file generated by Shopify (served from `cdn.shopify.com/…`), and no `section-*.css` links inside `<body>`.
2. Open quick view / predictive search / add to cart: elements are styled. If something is unstyled, that liquid file is scoped but its HTML arrives via AJAX → add it to `exclude`.
3. Open a collection and a product page: the generated file differs from the home page's (subset per page).
